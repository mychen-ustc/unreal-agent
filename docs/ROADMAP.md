## 1. 双时间轴总览

本项目同时存在**两条独立推进的轴线**，它们共用同一套「能力包」（UE MCP Toolset + Common Spec Skill），但节奏与目标不同：

| 轴线 | 主线 | 回答的问题 | 负责人侧 |
|---|---|---|---|
| **工程里程碑（P0–P6）** | 把「多 Agent 系统 + 参考游戏」从地基做到发布 | 系统能不能做出可玩、高品质、可打包的游戏 | 技术 / 产品 |
| **商业/资产保护里程碑（C0–C3）** | 把「能力包」从自用做到可付费交付 | 怎么变现、怎么防破解、怎么让客户拿不到核心资产 | 产品 / 商务 / 架构 |

> **关键关系**：这两条轴线**在时间上并行，在资产上耦合**。工程轴先打通能力包（P0–P1），商业轴才能在上面做交付（C1 起）。两条轴共用 `distiller`（能力蒸馏）、License/计量（trace/metering）等横切组件，因此里程碑需要「联动评审」对齐（§4）。

```
时间 →
工程轴   P0地基 ──▶ P1核心工具链 ──▶ P2策略组 ──▶ P3多智能体 ──▶ P4实战打磨 ──▶ P5发布 ──▶ P5+后验 ──▶ [P6 UE6 迁移]
         (本阶段)                    (垂直切片)             (完整关卡)   (可提交包)
商业轴         C0 能力包成型 ──▶ C1 能力蒸馏+引流 ──▶ C2 纯SaaS上线 ──▶ C3 私有化黑盒
              (内部自用)          (Demo/体验)           (付费主形态)      (高价值交付)
```

## 2. 工程里程碑（主时间轴 P0–P6）

> 沿用 PRD §7 的口径（周 / 时间线）。每个里程碑的「验收标准」见 [PRD §9](./AI_Agent_Game_Dev_PRD.md#9-验收标准) 与 [参考游戏 §7](./reference-game.md#7-验收与交付标准)，这里只给阶段目标与关键交付。

| 阶段 | 周期 | 目标 | 关键交付 | 验收锚点 |
|---|---|---|---|---|
| **P0 地基** | 第 1–4 周 | MCP 打通、首个 Toolset、安全体系 | ProjectToolset + SafeguardToolset 可用；Agent 能安全改关卡并回滚 | PRD AC-P0-01~06 |
| **P1 核心工具链** | 第 5–12 周 | PCG + Level Designer + Lighting + Asset Retrieval + Build/Test + RAG | Level Designer 产出 Blockout；PCG 图可由 Agent 生成并执行；灯光自动化；编译测试自动化 | PRD AC-P1-01~08 |
| **P2 策略与研究组** | 第 13–18 周 | S1–S6 Strategy & Research Agent 上线；首份《游戏概念提案》产出 | 市场报告 + 竞品矩阵 + 玩法方案 + 商业模型 + 技术评估 + 创意方向全部自动化 | PRD AC-P2-01~07 |
| **P3 多智能体** | 第 19–30 周 | 33 个 Agent + Orchestrator + 依赖 DAG 联调；**垂直切片**；评估组 + 回退闭环 | 端到端流水线（提案→垂直切片→可玩关卡）；变更传播与评估触发自动生效；产出参考游戏可玩切片 | PRD AC-P3-01~11；参考游戏 AC-REF-01 |
| **P4 实战打磨** | 第 31–42 周 | 外部生成模型接入、质量控制、评估组上线；以参考游戏完整关卡为验证产物 | 完整关卡由 AI 驱动生成；评估组多画像批判 + 横向对标通过；人工介入率 < 20% | PRD AC-P4-01~04；参考游戏 AC-REF-02~04 |
| **P5 发布准备** | 第 43–52 周 | 优化、打磨、平台适配 | 参考游戏产出可提交包体（验证工具链发布能力） | 参考游戏 §7 交付 |
| **P5+ 运营与后验** | 上线后 | 后验评估（立项预测 vs 实际）、运营期平衡调整、二次开发 | 预测偏差写回长期记忆改进立项；热更新/平衡调整自动触发 | 后验复盘记录 |
| **P6 UE6 迁移** | 2027+ | Verse + Scene Graph 适配 | 核心逻辑迁 Verse；MCP 架构复用 ≥ 80% | TechDesign §12 |

> 周期以「50 周 ≈ 12 个月」为基准（PRD §7 对齐架构 §8）。UA5.8 为 UE5 末代 LTS，UE6 Early Access 预计 2027 年末（见 §5）。

## 3. 商业 / 资产保护里程碑（并行时间轴 C0–C3）

> 这**不是**工程轴 P0–P6 的改名，而是独立的一条并行线：它回答「能力包如何变现且不被破解」，依赖工程轴把能力包打通。商用形态 A/B/C 的定义见 [Agent Harness §11](./agent-harness-selection-and-design.md#11-商业交付形态与资产保护)。

| 阶段 | 触发条件 | 目标 | 关键交付 | 与工程轴联动 |
|---|---|---|---|---|
| **C0 能力包成型（内部自用）** | 工程 P0–P1 | 能力包可本地跑通，注入至少 1 个第三方宿主作 Canary | Common Spec Skill（含 `tier`/`distill_visibility`）；UE MCP Toolset 稳定；`importers/` 首个 Adapter | 依赖 P1；预埋 `distiller` 骨架 |
| **C1 能力蒸馏 + 引流（Demo/体验）** | 工程 P1 后半 | 蒸馏出「最小可用版」（Tier ≤2 + Tier 0）作对外 Demo；不泄露核心 | `distiller.py` 落地；Skill 五级（Tier 0–4）定级完成；`importers/` 多宿主 Adapter；引流子集质量门 | 联动 P1；Gateway/权限/计量预埋 |
| **C2 纯 SaaS 上线（付费主形态）** | 工程 P2–P4（能力包成熟）| 多租户托管；客户经 API/Web 使用，能力包不出境；按租户配额计费 | 多租户沙箱（Firecracker/Pod）+ 唯一写入者；租户计量/计费；Skill/工具面运营 | 联动 P2–P4；复用 §9 多租户 |
| **C3 私有化黑盒（高价值交付）** | 能力包 + 引擎定制稳定后 | 完整能力包（完整 UE Runtime + 引擎定制）跑客户机器/VPC，**不调用你的服务**；核心资产不可见 | 黑盒镜像/二进制 + MCP 契约 + License/心跳/脱敏回传；《交付物边界声明》；更高价 + 协议约束 | 依赖引擎级定制（P5/P6 侧）；复用 Durable/计量 |

### 3.1 资产保护贯穿线（C1–C3 均适用）

| 保护手段 | C1 引流 | C2 SaaS | C3 私有化黑盒 |
|---|---|---|---|
| 能力蒸馏（只出低价值子集） | ✅ 核心 | 不适用（不出境） | 不适用 |
| 完整能力包不出境 | ✅（子集才出） | ✅（API 即结果） | ⚠️ 黑盒运行于客户侧，靠逆向成本 + 协议兜底 |
| Toolset 混淆 / 引擎级定制保护 | 部分 | 天然安全 | ✅ 隐形于 UE 源码 |
| License / 计量 / 心跳 | ✅ 子集水印 | ✅ 租户计量 | ✅ 容器内强上报 |
| 数据飞轮留在服务端 | ✅ | ✅ | ✅（脱敏回传） |

### 3.2 P0 预埋的商业钩子（防 C1/C2/C3 返工）

> 商业化完整逻辑不在 P0 实现，但**几个钩子在 P0 代码里就要预留**，否则 C1（蒸馏）/C2（计费）/C3（私有化）只能补历史债。落地见 [ops/SECURITY-LICENSING](./ops/SECURITY-LICENSING.md)。

1. **计量标签**：Tool/Agent/长任务/模型调用事件，现在就把 `tenant_id / license_key / duration / token_usage / model_tier` 字段放进事件结构（P0 值可为空，只留位）。
2. **审计必可追溯、防篡改**：模型/Tool/审批全量落 trace，追加写不改历史行。
3. **Skill 分级字段**：`skill.yaml` 现在就声明 `tier (0–4)` + `distill_visibility (full|lite|hidden)`，即便 P0 只有 `scenes_pcg` 也先定级。
4. **`distiller.py` 骨架**：P0 建函数签名 + `tier<=2` 裁剪逻辑的可运行骨架，让"它应该在"被明文落位。
5. **审计 vs RAG 语料分离**：二者存储独立，审计不可篡改、RAG 可重建（红线）。

## 4. 里程碑对照与联动

工程轴与商业轴在某些点必须同步评审，否则会互相阻塞：

| 联动点 | 工程轴 | 商业轴 | 需要一致化的东西 |
|---|---|---|---|
| 能力包首发 | P0–P1 | C0/C1 | `skill.yaml` 的 `tier`/`distill_visibility` 定级；`importers/` 范围 |
| 计量 / License 设计 | P1–P4 | C1 起 | trace/metering 标签统一；多租户与黑盒共用一套计量 |
| 多租户 / 并行写 | TechDesign §9 | C2 | 空间分区 + 单写入者在多租户下复用（TDR-H06） |
| 完整 UE Runtime / 引擎定制 | 架构 §0 / P5+ | C3 | 引擎级定制既是工程蓝图，也是黑盒核心壁垒 |
| 参考游戏发布 | P5 | 可选做样板 | 参考游戏可同时作为「能力包商业化」的成功案例/白标 |

## 5. UE6 远瞻

> UE6 Early Access 预计 2027 年末，稳定版约 2028–2029。三大支柱：Verse 语言、开放内容可移植性、内置 AI/MCP。蓝图 + 传统 Actor 逐步被 Verse + Scene Graph 替代。

- **P6 迁移目标**：核心逻辑迁 Verse；MCP 架构层（L1 适配）复用 ≥ 80%（TechDesign §12 / 架构 §8）。
- **能力包不变**：UE MCP Toolset + Common Spec Skill 与引擎版本解耦，迁移面锁在 L1 `EngineBridge` 适配层。
- **引擎级定制的延续**：本项目规划对 UE 做引擎级 AI 定制（推理嵌渲染/校验、定制沙箱、扩展 PCG），这部分既是 P5+ 的工程蓝图，也是 C3 私有化黑盒的核心壁垒，须与 UE6 迁移并行规划（避免定制方式与 UE6 架构冲突）。

## 6. 阶段横切关注点

每个阶段都应达标以下横向质量（在验收时一并检查，不另设专属里程碑）：

| 关注点 | 说明 | 主要来源 |
|---|---|---|
| **安全 / 治理** | 沙箱、风险分级、Git 钩子、审批门、回滚 | TechDesign §7、PRD §4.1.2 |
| **可观测 / 计量** | OTel trace、trace.jsonl、License/租户计量标签 | TechDesign §10、Agent Harness §11 |
| **可测试** | 单元/集成/端到端/evals 金字塔 + 录制回放 | TechDesign §10.2 |
| **可维护 / 可替换** | 模型、向量库、编排宿主、Toolset 适配都可换 | TechDesign §12 |

## 7. 职责与评审节奏

- **阶段 gate**：每个里程碑交付时，产品 + 技术 + 商务（涉及商业轴时）共同过 gate，对照 §2/§3 的关键交付与各自验收项。
- **联动评审**：在「能力包首发」「计量设计」「多租户」「私有化黑盒」4 个联动点强制双向对齐（§4）。
- **文档维护**：阶段推进时同步更新 [PRD](./AI_Agent_Game_Dev_PRD.md)、[TechDesign](./AI_Agent_Game_Dev_TechDesign.md)、[Agent Harness](./agent-harness-selection-and-design.md)、[参考游戏](./reference-game.md)，本路线图只维护「阶段号与联动」这一层。
